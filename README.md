# Agent Run Semantics Contract v0.5.0（提案 / proposal）

**A cross-language reliability contract for agent runs** — states & legal transitions, idempotency scope, integer micro-USD budget with `reserve → settle`, JCS-hashed audit chain, capability-tiered tools, and a first-class `outcome_unknown` state that **cannot silently re-enter execution**.

> **Status: v0.5.0-draft.** The three hard defects from review 01 are fixed and verified; the contract now includes a replayable audit chain. Seeking **≥2 independent human maintainer / implementer reviews**.

## What is new in v0.3.0 → v0.5.0 (all from review 01, all verified)

| Review finding | What changed |
|---|---|
| Validator never read `status-transitions.json`; fixtures disagreed with each other | The transition table is now the **authoritative source** both implementations read; every fixture must equal it, or CI fails |
| Fixture audit hashes were placeholders and did not match our own formula | Audit hashing is now **`sha256(JCS([seq, ts_ms, type, run_id, step_id, attempt, JCS(payload), prev_hash]))`** (RFC 8785), all fixtures recomputed, and a tampered-chain fixture must be rejected at `/run/audit/<i>/hash` |
| "Two implementations, byte-identical" was only a claim | Both implementations (independent Python and Java) emit **byte-identical output** for `--all`, `--schema`, `--coverage`, `--fields`, `--digest` (26 fixtures), `--verify-chain`, and `--replay`. The **Java-generated golden output is committed in [`tools/golden/`](tools/golden/)** — see *Verify it yourself* below |
| `reserve → settle` existed only in prose | `$defs/reservation` + `run.reservations` are in the schema; retry reuses the same reservation id; price snapshot frozen per reservation |
| `step` was a single object while docs said `step[]` | `step` is an **array**; a multi-step fixture proves it |
| `ts` had no format and entered the hash | Timestamps are `ts_ms: integer` (epoch ms) — no timezone/format divergence possible |
| `outcome_unknown → running` was legal (safety hole) | **Removed and blacklisted** (`forbidden`): the validator fails if anyone adds it back |
| Missing edges (`created → waiting_approval`, `paused → failed`, `degraded → …`, `outcome_unknown → cancelled`) | Added; `outcome_unknown → succeeded/failed` requires an `evidence_ref` from reconciliation |
| Canonical JSON conflicted with JCS | JCS is adopted for hashing (including UTF-16 code-unit key ordering); floats are allowed in tool args (only money stays integer micro-USD) |
| Tool capability tiers were our own vocabulary | v0.5.0 folds them into **MCP `ToolAnnotations`** (`readOnlyHint`/`destructiveHint`/`idempotentHint`/`openWorldHint`), with validators enforcing consistency and keeping `openWorldHint` as the predictor of `outcome_unknown` |
| `audit_payload.result` was free text hashed as-is | v0.5.0 replaces it with **`result_digest`** (sha256 of canonical bytes) — identical results can no longer hash differently |
| Audit chain could not be checked against the state machine | **`--replay`**: every `state_transition` entry is replayed in order; first `from` must be `created`, edges must be legal, and leaving `outcome_unknown` requires `evidence_ref`. Tampering with a transition breaks both the hash chain and the replay |

Version history and evidence: [`CHANGELOG.md`](CHANGELOG.md) · review dispositions: [`REVIEWS/`](REVIEWS/).

## Verify it yourself (2 minutes)

```bash
python -m pip install "jsonschema>=4.20"
python tools/contract_check.py --all     # valid 14/14 · invalid 14/14
python tools/check_versions.py           # version consistency (id/title/enum/transitions/CHANGELOG)
python tools/check_golden.py             # Python impl vs Java-generated golden: 35/35 byte-identical
```

`tools/golden/` is **generated by the independent Java implementation** (not copied from Python): 7 command outputs, 28 per-fixture digests, exit codes for 35 cases, and a `MANIFEST.json` with sha256 per file. `tools/check_golden.py` reruns every case with the Python implementation and compares **bytes** — any divergence fails CI. This is the answer to review 01's "your two implementations are both yours" objection: agreement is now checkable by a third party, in this repository.

## Why this exists

Protocols standardise *how agents talk* (A2A) and *how long-running tool calls are tracked* (MCP Tasks). They deliberately leave to implementations the decisions that determine whether a retry is safe. This repo proposes those as an **interoperable contract** — and, since v0.4.0, one thing that can be *checked*: an audit chain that replays into a legal state sequence.
